## Issues

### 1. Combo cancellation restocks from the live recipe, not the order's snapshot

**File:** `Backend/orders/views.py:96` (in `restore_order_stock`)
**Severity:** High — silent inventory corruption

`OrderItemComponent` (new in this diff) snapshots exactly what a combo line drew
from stock — `variant` + `quantity`, documented as *"TOTAL units of this size the
line consumed: per-combo quantity x line quantity, matching what was drawn from
stock."* It is written at checkout (`orders/views.py:740`) and read by
`order_tax_breakdown`.

But the restore path ignores it:

```python
for ci in ProductComboItem.objects.filter(combo=item.combo).select_related('variant'):
    variant_updates[ci.variant_id] = (
        variant_updates.get(ci.variant_id, 0) + ci.quantity * item.quantity)
```

This reads the combo's composition **as it is today**. If an admin swaps a
component size, changes a per-combo quantity, or adds/removes a component between
order placement and cancellation, the cancel credits the wrong variants — silently,
and in both directions: phantom stock on one SKU, permanently lost stock on
another.

This is the same class of bug the G2 product→variant fix in this same diff was
written to close. The snapshot that fixes it already exists and is already
populated; the restore path just isn't wired to it.

#### Solution

Prefer the snapshot; fall back to the live recipe only for historical lines that
predate it (the model docstring already anticipates that fallback).

```python
# orders/views.py — in restore_order_stock()

    for item in order.items.select_related(
            'product', 'combo', 'variant').prefetch_related('components').all():
        if item.item_type == 'product' and item.variant:
            variant_updates[item.variant.pk] = variant_updates.get(item.variant.pk, 0) + item.quantity
        elif item.product:
            product_updates[item.product.pk] = product_updates.get(item.product.pk, 0) + item.quantity
        elif item.combo:
            # G2 symmetry: give back exactly what checkout drew. OrderItemComponent
            # is that record — the combo's recipe can be edited after the order is
            # placed, so re-reading it here would credit the wrong sizes.
            snapshot = list(item.components.all())
            if snapshot:
                for comp in snapshot:
                    # comp.quantity is ALREADY the total consumed (per-combo qty x
                    # line qty). Multiplying by item.quantity again would over-credit.
                    variant_updates[comp.variant_id] = (
                        variant_updates.get(comp.variant_id, 0) + comp.quantity)
            else:
                # Historical line placed before the component snapshot shipped —
                # the live recipe is the only record we have.
                for ci in ProductComboItem.objects.filter(
                        combo=item.combo).select_related('variant'):
                    variant_updates[ci.variant_id] = (
                        variant_updates.get(ci.variant_id, 0) + ci.quantity * item.quantity)
```

**Trap to avoid:** `OrderItemComponent.quantity` is already the *total* units
consumed (per-combo quantity × line quantity), unlike `ProductComboItem.quantity`
which is per-combo. Multiplying the snapshot by `item.quantity` — the natural
copy-paste from the branch above — silently over-credits stock on every
multi-quantity combo cancellation.

**Test to add:** place a combo order, mutate the combo (swap a component's
variant, or change its `quantity`), cancel, then assert the *originally ordered*
variants got their stock back and the newly-swapped one did not.
`orders/test_checkout_and_ops.py::TestComboCancelRestocksVariants` is the natural
home — it already builds the fixture.

### 2. Gateway refunds strand inventory with no recovery path

**Files:** `Backend/orders/refunds.py:120` (in `record_refund`),
`Backend/orders/views.py:122` (`UNCANCELLABLE_STATUSES`)
**Severity:** High — unrecoverable stock loss on dashboard-issued refunds

`record_refund` sets `order.status = 'refunded'` on a full refund and never calls
`restore_order_stock`. Its docstring says restocking is *"left to the admin/cancel
flow"* — but this same diff added `'refunded'` to `UNCANCELLABLE_STATUSES`:

```python
UNCANCELLABLE_STATUSES = {'delivered', 'delivering', 'cancelled', 'refunded'}
```

So once the status flips, there is no cancel flow left to reach.

- **Admin path** — recoverable only if they happen to cancel *before* marking
  refunded. `cancelled → refunded` works; `refunded → cancelled` is blocked.
  An easy trap to fall into in the wrong order.
- **Razorpay dashboard path** — no window at all. `refund.processed` arrives,
  `mark_payment_refunded` → `record_refund` flips the order terminal, and the
  stock is never returned.

#### Solution

Restock inside `record_refund` on the transition into fully-refunded. That covers
**both** callers — the admin status flip and the Razorpay webhook — from one
place, which is the same reason the ledger owns the GST reversal and the status.

```python
# orders/refunds.py — in record_refund(), replacing the `if fully_refunded:` block

        if fully_refunded:
            # Restock BEFORE flipping status, and only on the transition — a
            # second refund event, or an order already cancelled (which restocked
            # on the way through), must not credit the inventory twice.
            if order.status not in ('cancelled', 'refunded'):
                # Local import: orders.views imports this module at module level.
                from .views import restore_order_stock
                restore_order_stock(order)

            order.status = 'refunded'
            fields.append('status')
            if order.payment_status != 'refunded':
                order.payment_status = 'refunded'
                fields.append('payment_status')
```

Notes on the shape of this fix:

- **The `('cancelled', 'refunded')` guard is load-bearing.** `cancelled → refunded`
  is a legitimate admin sequence and already restocked; without the guard it would
  double-credit. A redelivered webhook is separately protected by the `reference`
  unique constraint, but the guard makes the invariant explicit.
- **The local import** is required — `orders/views.py` does
  `from .refunds import record_refund, refundable_balance` at module level, so a
  top-level import here is a cycle. Cleaner long-term: move `restore_order_stock`
  into an `orders/stock.py` that both modules import.
- `record_refund` already holds `select_for_update()` on the order inside its own
  `transaction.atomic()`, which is exactly the contract `restore_order_stock`
  documents ("MUST be called inside a `transaction.atomic()` block with `order`
  already locked"). No extra locking needed.
- Leave `'refunded'` in `UNCANCELLABLE_STATUSES`. Once this fix lands the status is
  genuinely terminal *and* correct — reopening it to cancellation would reintroduce
  the double-restock it was added to prevent.

**Tests to add** in `orders/test_refunds.py`:
1. Gateway `refund.processed` on a paid order → variant stock returns to its
   pre-order level.
2. `cancelled → refunded` → stock credited exactly **once**.
3. Two `refund.processed` deliveries with the same `reference` → stock credited
   exactly once.

### 3. N+1 query on the order list

**Files:** `Backend/orders/views.py:195` (admin scope), `:214` (customer scope)
**Severity:** Medium — performance

Both order serializers now nest refunds:

```python
refunds = OrderRefundSerializer(many=True, read_only=True)
```

...but neither queryset prefetches them:

```python
.prefetch_related('items__product', 'items__combo', 'items__variant')
```

That is +1 query per order on every list page — 12 extra per page at
`PAGE_SIZE=12` — on both the admin order table and the customer "My Orders" view.

#### Solution

Add `'refunds'` to both `prefetch_related(...)` calls. Add `'items__components'`
at the same time — `order_tax_breakdown` reads `OrderItemComponent` rows for combo
lines, which is a second N+1 on any order list containing combos, and the fix for
Issue 1 makes `restore_order_stock` read them too.

```python
# orders/views.py:195 — admin scope
            qs = Order.objects.all().prefetch_related(
                'items__product', 'items__combo', 'items__variant',
                'items__components', 'refunds',
            ).select_related('user', 'payment')

# orders/views.py:214 — customer scope
        return Order.objects.filter(user=user, is_deleted=False).prefetch_related(
            'items__product', 'items__combo', 'items__variant',
            'items__components', 'refunds',
        )
```

`items` itself *is* already prefetched, so the CSV export is fine as written.

**How to verify:** wrap a list call in `django.test.utils.CaptureQueriesContext`
and assert the query count is flat as the page fills — seed 1 order, then 12, and
confirm the count doesn't grow with the number of orders.
